# 考勤同步并发风险与优化方案

> 背景:在评估"hainan HR SaaS 是否应微服务化"时,第 2 点风险为——**所有分公司在每月 1 号同时考勤打卡的并发风险**。本文记录问题、澄清、分析、结论与最优优化方案。
>
> 【2026-08-30 实施后更新】本方案已于当日全部落地(考勤+审批),文中各条目已标注实施状态;新增第 5 节"速度影响分析"。

## 1. 原始问题
- 在"系统能否重构为微服务/多子系统"的评估中,用户聚焦第 2 点:**所有分公司在 1 号上班、同一时间同步考勤,这里有什么风险?** 隐含诉求:判断"拆微服务"能否缓解该风险。

## 2. 澄清答复(用户原话要点)
- **生产规模**:本项目服务于一个由 **4 家公司**组成的集团,后续可能再增 **3~4 家**(共 ≤8 家);**每家公司员工数最多 400~500 人**。→ 全集团峰值 ≤4000 人。
- **打卡入口**:并非员工实时打点,而是**管理员在后台触发**:
  - 员工管理功能中的 **「同步考勤」按钮**;
  - 考勤管理 → 审批数据中的 **「获取审批数据」按钮**。
  - 两者都是**去钉钉拉取数据**写回本地库。
- **方案取向**:「哪个方案最优选用哪个方案」(以最优为准则,不预设微服务)。
- 【实施后补充的硬性要求】若 8 家公司真的同一时间开始同步:**数据之间不能打架,各分公司的钉钉数据必须落入各分公司对应的租户库和表**;且不允许任何一家被"排队等待"。

## 3. 代码与运行态实证分析(只读探查结论)
### 3.1 规模与数据链路已不是瓶颈
- 单公司 ≤500 人,全集团 ≤4000 人;打卡数据写各公司**独立租户库**(`hr_0001`…`hr_0005` 同实例但分 schema),批量 `saveBatch` 落库。该量级对 MySQL 写入无压力。
- MySQL `max_connections=151`;连接池经 `DataSourcePoolConfigurator` 限定为**每租户 `maximumPoolSize=8`、`minimum-idle=0` + LRU 驱逐**(`CompanyDataSourceProvider`)→ 8 家同时同步的连接上界 ≈ 主池 60 + 8×8 = 124 < 151,**不会出现连接耗尽**。

### 3.2 钉钉按公司独立应用 → 跨公司不限流叠加
- `DDAccessToken.Refresh()` 按 `CompanyContext.get().getCompanyId()` 过滤 `ddAccount`,取各自 `appKey/appSecret` 换取 token。**每家公司是独立的钉钉应用**。
- 因此 8 家公司同时点同步 = 打 8 个不同钉钉应用,**各自限流互不影响**。"全分公司同一时间同步"**不会**在钉钉侧叠加 QPS,跨公司限流风险不成立。

### 3.3 钉钉限流逻辑处理情况【原文有误,已修正】
- 考勤主链路(`HrmAttendanceDataServiceImpl`):`PARALLEL_THREADS=2`、钉钉明细接口按 50 人批量、多处 `Thread.sleep` 节流、失败退避重试——**原结论"已充分"成立**,本轮未动。
- 审批链路(`HrmAttendanceApprovalSyncServiceImpl`):原文"已内置限流提示"不准确——它只能**识别**限流错误文案,链路本身串行、无 sleep、无限流。**本轮已补**:三处外呼(拉审批模板/分页拉实例 ID/逐实例取详情)后统一间隔 100ms。

### 3.4 真正的风险点(原文两点的最终状态)
1. **同步是同步阻塞 HTTP 请求**(关键)——原文成立。【已解决】`/sync`、`/syncAll`、`/fetchMonthData` 均改为**提交后台任务后立即返回**,HTTP 请求线程不再被长占,超时/卡 UI 问题消除。
2. **同公司可能被重复触发**——原文成立("仅靠 Redis 断点进度,无互斥锁")。【已解决】提交路径同步抢占**按公司 Redis 锁**(`attendance:sync:running:<companyId>`,TTL 2 小时,任务 finally 释放;进程崩溃最多 2 小时自动放行),同公司连点第 2 次当场返回"正在进行中"。
3. 【实施中发现的隐藏风险,原文未列】**同步进度键是全局键**:进度/断点/状态 Redis 键均不带 companyId,若只做"按公司锁"而改进度键,跨公司并发会互相覆盖进度条与断点。**本轮已一并处理**:全部 11 个同步进度键追加 `:companyId` 后缀,进度按公司隔离。

### 3.5 关于"拆微服务"的结论
- **对第 2 点风险,拆微服务零收益且有运维成本**(写流量仍落同一 MySQL 实例、钉钉仍按公司独立,微服务不增加 DB/钉钉容量;限流、热点、连接池问题单体内即可解)。
- 不需要 DB 分片(量小)、不需要独立考勤服务。

## 4. 最优优化方案(单体内向,最低侵入)——【已全部实施】
> 核心:把"同步"做成**异步 + 每公司互斥锁 + 进度键按公司隔离**;其余(钉钉限流、DB、分库)维持现状。

### 4.1 改动清单(实施状态)
1. 【已实施,参数修正】**托管线程池 `AttendanceSyncTaskLauncher`**:核心=上限=**8**(≈分公司数上限,保证 8 家同时提交全部立即并行,**不因超出核心数排队**)+ 队列 8;拒绝策略为 **AbortPolicy**——原文拟用 `CallerRunsPolicy`,实施时发现它与"立即返回"自相矛盾(队列满时任务会跑回 HTTP 请求线程),改为队列满直接返回"系统繁忙,请稍后再试"。
2. 【已实施】考勤与审批的同步任务由该线程池执行,异步线程恢复 `CompanyContext` 后调用既有 `SyncData`/`fetchMonthData`,**断点续传、批量、重试等内部逻辑零改动**。未采用原文的 `@Async` 方案(项目未启用 `@EnableAsync`),改为与 `WorkPlanServiceImpl` 一致的显式线程池模式。
3. 【已实施】`/sync`、`/syncAll`、`/fetchMonthData` 提交后**立即返回** `{queued:true, queuedAt:<服务端时间戳>}`,提示"同步已开始,请通过进度条查看进展"。
4. 【已实施,粒度修正】**按公司互斥锁** + **锁在提交路径同步抢占**(原文未写明抢占时机——若在异步任务里抢,重复点击会先收到"已启动"再静默失败)。锁键:`attendance:sync:running:<companyId>`(考勤)/ JVM 内按公司标记(审批,超 2 小时视为异常残留自动放行)。
5. 【已实施】审批「获取审批数据」同样异步 + 按公司锁 + 100ms 节流(确认过其触发亦为同步阻塞)。
6. 【原文描述已过时】线程池"未 shutdown"实际正常路径存在,异常路径泄漏已于同日先行修复。
7. 【实施幅度大于原文预期】前端**不是"基本不动"**:考勤同步页的完成信号原本绑定在触发响应上(`res.code===0` 即报"同步完成"),异步化后改为**轮询进度直至完成**——完成判定条件为 `done && updateTime >= queuedAt`(queuedAt 为本次提交的服务端时间戳,防止读到上一次运行 24 小时内的旧 SUCCESS 状态而瞬间假完成);排队期显示"已提交,正在排队准备同步数据..."。审批页原本就有进度轮询,仅补等待循环。
8. 【实施后修正】线程池核心数最初设 4,会使第 5~8 家公司的任务**进入队列等待**(Java 线程池超出核心数的任务先入队),违背"8 家同时并行"的硬要求,已修正为核心=上限=8。
9. 【实施后追加】**失败自动重试**:后台任务失败后自动重试(默认 2 次,指数退避 60s 起步、封顶 5 分钟,可配);重试等待期进度保持 RUNNING 并显示"正在自动重试",仅最终失败置为 FAILED。考勤重试**从断点续传**(已完成步骤不重拉),审批重放**幂等**(按审批实例主键跳过已入库记录)。参数类错误("请选择...")与队列繁忙不重试。前端轮询上限放宽至 60 分钟。

### 4.2 明确不做
- 不抽微服务、不做 DB 分片、不改考勤同步内部限流参数(PARALLEL_THREADS=2、50 人批量、sleep 节流保持)。

### 4.3 风险与回滚
- 改动仅涉及控制层 + 一个托管线程池/锁组件 + 进度键命名 + 前端完成信号,可灰度。
- 回滚 = controller 调回同步 `SyncData` 即可,无数据迁移。
- 【新增注意事项】进度键带 companyId 后,发布当天的旧全局进度键自然失效一次(断点续传从零开始一次),无数据影响。

### 4.4 验证步骤
- 本地用 2 个公司**同时**点同步 → 各自完成、互不干扰(进度条各显各的);
- 同公司连点 2 次 → 第 2 次被锁拒绝;
- 拉整月长区间不触发 HTTP 超时(触发请求秒回);
- 各公司 `hrm_attendance_clock` 无重复行;
- 【新增】8 家同时提交 → 8 个任务全部立即开始(可观察日志 `公司XX考勤同步已提交后台执行`),无排队等待。

## 5. 速度影响分析(补充:完成一次同步所需时间的变化)

> 前提:本轮**刻意不改**考勤同步内部的钉钉拉取参数(2 线程/50 人批量/节流),因此"单家公司拉一次数据"的主体时长基本持平。变化体现在以下四个层面(未实测,为代码推算,1 号上线后可按 `updateTime/queuedAt` 记录实测):

1. **点击到界面响应(用户体感)**:从"请求阻塞到同步完成"(几百人全月约 3~15 分钟,期间转圈、可能网关超时)变为**毫秒级返回**"已开始"。这是最大体感变化。
2. **单公司同步完成时长(后台实际拉完)**:
   - 基本持平:钉钉外呼次数与节流参数未动;
   - **略有加快**:打卡/考勤明细落库的逐条 `findById` 改为按页批量(每页 2 条 SQL 代替 2×页内条数)——一个月 1 万条打卡记录的公式约为"原来 2 万次主键查询(按 1~3ms/次 = 20~60 秒)→ 现在近零",明细占大头的月份预计**缩短数十秒**;
   - **失败场景数量级加快**:钉钉返回失败时原实现会死循环**永不结束**,现在 3 次重试(约 3 秒)后快速失败并保留断点。
3. **审批「获取审批数据」完成时长:故意变慢一点**——三处外呼后新增 100ms 间隔。按全月 500 人、约 2500~3000 次外呼估算,**额外约 4~5 分钟**。换来的稳定性:改造前一旦触发钉钉频控,整批失败需全部重拉(失败一次等于全部时间 ×2);现在稳定跑完。且它在后台异步执行,不占操作人员等待。**综合期望完成时间(含重试)通常反而更短**。
4. **1 号早高峰全集团并发吞吐(核心收益)**:
   - 原始版本:8 家同时点可并行但进度键互相覆盖(断点全废、进度条串台);
   - 上一批修复后:全局锁让 8 家**串行**,第 N 家要等前 N-1 家跑完;
   - 本轮:8 家**真并行**,设单家同步 T 分钟,全集团最后一家完成时间从 ≈8T 降到 ≈T,**集团吞吐约提升 8 倍**(线程池上限 8 保护,第 9 个及以后提交返回"繁忙")。

### 5.1 钉钉官方限流文档对照(8 家并发会不会有问题)

依据钉钉开放平台官方文档《调用频次与限流》《调用频率限制》,限流分四个维度:

| 维度 | 官方数值 | 8 家并发的实际压力 | 结论 |
|---|---|---|---|
| 应用维度 | 每应用 **20 QPS**(标准版组织,服务端接口) | 每家是独立钉钉应用,单家峰值 ≈7~12 QPS(主线程+2 worker),**互不叠加** | ✅ 安全 |
| IP 维度 | 每公网出口 IP 所有接口合计 **20 秒 10000 次(≈500 QPS)**,触发后**封禁该 IP 全部接口 5 分钟** | 8 家同源 IP,叠加 ≈64~100 QPS | ✅ 余量 ≥5 倍;注意这是全系统所有钉钉调用共享的硬顶 |
| 接口全局维度 | 所有企业所有应用调**同一接口**超限 → 90002,**阈值官方未公开** | 8 家打同一接口(如 attendance/listRecord)叠加 ≈24~64 QPS | ⚠️ 无法从文档证实阈值;即使偶发触发,现有"3 次退避+快速失败+断点续传"保证不死循环、不雪崩,最坏单家当次失败重试即可 |
| 月配额 | 标准版免费 **10000 次/自然月/应用**,可官方增购 | 每家消耗**自己应用**的配额,互不叠加;单公司 1 号全量(考勤+审批逐实例)可能逼近 1 万 | ⚠️ 系统已有 80% 用量提醒(`dingtalk.api.monthly-limit`);不够需增购 |

- 对照后的修正项:排班同步 `attendance/listschedule` 分页循环原先**无 sleep**,网络快时单公司自己就可能贴住 20 QPS 上限——已补 100ms 节流,单公司峰值压到 ≈8~10 QPS,安全边际一倍以上。
- 总结论:**8 家并发不会带来新增的钉钉侧风险**(每应用独立、IP 余量充足);唯一不可证实的是接口全局池阈值,已有失败兜底。若未来公司数超过 ~15 家或需压缩同步时长,可走官方《服务端 API 流控工具》申请提升阈值。

## 6. 一句话结论
> 第 2 点风险的根源是"同步考勤/获取审批"为**同步阻塞 HTTP 触发** + **缺少按公司互斥与进度隔离**,而非钉钉/DB 容量;钉钉按公司独立、规模小。**最优解=异步任务 + 按公司互斥锁 + 进度键按公司隔离(单体即可),已全部落地;拆微服务不解决问题且增加成本。** 单公司拉数据主体时长基本持平(明细批量化略有加快、审批因防频控故意放慢约 100ms/次),真正的收益在"点击立即响应 + 1 号 8 家并发互不干扰 + 失败快速退出可断点续传"。
